# 작전실 실측과 정상·금지 요청 표를 만드는 절차

이 문서는 현재 누적 정책의 재검사 절차입니다. 과거 단계의 공식 통과를 소급하지 않습니다. `public/operations-model.mjs`의 1~11단계 정상·금지 22행 계획은 공식 41종 공격 목록이 아닙니다. 공식 목록·실행 결과가 없으면 41종 전체를 미실행으로 남깁니다.

## 커밋과 공개 API 관측

1. `git status --short`로 다른 작업 유무를 확인하고 `git log -1 --format=%H`로 검사할 코드 커밋을 정합니다. 커밋되지 않은 변경은 검사 커밋에 포함됐다고 표시하지 않습니다.
2. 저장점이 만들어진 뒤 `npm run operations:check`를 실행합니다. 실제 HTTPS 배포에 고정된 8개 요청만 보냅니다. 자료실 문서·manifest·세션 상태는 HTTP 200, 정적 data.json은 404, 무로그인 자료·기기 상태는 401, 공지 학생 경로 쓰기는 405를 기대합니다. 배포 manifest의 단계·저장소도 대조하며 현재 코드 커밋과 **응답 배포 커밋을 따로** 남깁니다. 이번 코드가 미배포라면 차이를 그대로 표시합니다.
3. 결과는 Git 제외 `artifacts/operations-evidence.json`과 `artifacts/operations-evidence.md`에 생성됩니다. 표에는 단계·정상/금지·기대 결과·실제 HTTP 결과·요청 ID·UTC 확인 시각이 있습니다. JSON과 표는 같은 관측 객체를 사용합니다. 같은 관측을 여러 행이 참조할 수 있지만 요청 건수는 중복 합산하지 않습니다.
4. `/operations.html`에서 **실제 API 다시 확인 → 가린 서버 관측 기록 펼치기 → JSON 내보내기**로 화면 수치와 기록을 대조합니다. `GET /api/operations`는 읽기 전용 메타데이터이며 15초 이내 같은 스냅샷을 재사용하면 ID와 시각도 그대로입니다. 서버리스 프로세스의 일시 관측이며 영속 감사 DB나 엔진 사건 이력은 아닙니다.

요청 ID는 관측 서버가 HTTP 요청 전에 생성해 `X-Request-Id`로 보낸 UUID입니다. 응답의 X-Request-Id가 UUID 형태로 존재할 때만 별도 upstreamRequestId로 남깁니다. 서버가 이 헤더를 자기 로그에 기록했거나 엔진이 같은 ID를 발급했다고 추정하지 않습니다. 원문 헤더·쿠키·오류 본문·토큰·실명·메모 본문은 기록하지 않습니다. 메모 읽기 결과도 상태 코드만 취하고 응답 본문은 파싱/저장하지 않습니다.

## 승인 계정의 정상·타인 요청

1. 등록부 SQL 준비 후 실제 A/B 시험 계정을 서로 다른 세션에서 로그인하고 해당 브라우저 기기를 신뢰된 관리자가 각각 승인합니다. 준비되지 않았다면 해당 행은 **미실행**입니다. 이 대화에서 실제 DB 준비·승인·계정 시험 완료는 확인되지 않았습니다.
2. 기존 자료실에서 각 계정이 자신의 가상 시험 메모를 준비하고 존재를 확인합니다. 본문·비밀번호·키를 보고서에 복사하지 않습니다. 기존 학습 메모를 삭제하는 시험을 자동 실행하지 않습니다.
3. 작전실의 **본인 메모 허용 확인**에 본인 시험 메모 ID를 입력하고 버튼을 눌러 HTTP 200을 확인합니다. **타인 메모 거부 확인**에는 상대 계정에서 존재를 확인한 메모 ID를 입력해 HTTP 404를 확인합니다. B의 A 메모 거부와 A 정상 허용은 두 계정에서 별도 실행해 JSON을 각각 안전한 위치에 보관합니다. ID는 전송에만 사용하며 관측 기록의 경로는 `/api/notes/:id`로 가립니다.
4. 기록의 expectedStatus와 httpStatus가 다르면 mismatch이며, 접속 실패는 request_failed입니다. 503을 403/401 차단 성공으로 바꾸지 않습니다. 없는 ID의 404만으로 타인 자료 차단이라고 주장하지 않습니다. 승인·세션 확인 실패 시 버튼은 잠기고 기록을 성공으로 채우지 않습니다.
5. 이 POST 제어 경로는 동일 출처의 세션/기기 쿠키가 있어야 하며, 서버가 고정된 자기 자료 API로 GET 한 건만 보냅니다. 요청의 외부 URL·복구 명령·본문·임의 HTTP 메서드는 받지 않습니다. 자료 API가 신원·기기 승인·소유자를 다시 검증합니다. 새 권한을 부여하지 않습니다.

## 아직 연결되지 않은 시험의 기록

- 3단계 실제 로그인, 5단계 원본 API 우회, 6~7단계 엔진 등록·재인증, 8단계 반 소속, 9단계 사건/회수 집행, 10단계 운영 B 사본 복구, 11단계 실제 설치/승인은 준비된 운영 계약과 증거가 필요합니다. 없으면 not_run입니다.
- `npm run decider:test`, `npm run detect:test`, `npm run recovery:test`, `npm run device:test`는 로컬 가상/모의 시험입니다. 그 통과 수를 실제 HTTP 표나 공식 41종 통과 수에 넣지 않습니다.
- 공식 41종 목록과 운영 엔진 감사/회수/복구 기록을 연결할 계약은 제공되지 않았습니다. 임의 테스트 이름 41개나 실행 결과를 생성하지 않습니다. 실제로 수행한 운영 시험만 요청 ID·확인 시각·고정된 상태/이유 코드와 함께 별도로 연결해야 합니다.
- 작전실의 복구 정보는 안전 사본 재검증 성공 여부와 configured/verified copy version입니다. 실제 운영 restoredLiveVersion과 회수 건수·탐지 사건 수는 증거가 없어 null입니다. null을 0건 성공 또는 안전 상태로 표시하지 않습니다.

## 재현 시험

`npm run operations:test`는 관측·화면 모델 수치 일치, 본문/ID/인증 값 제외, 성공 위조 방지, 대상 제한과 쿠키 출처 경계를 검사합니다. 실제 계정과 엔진 없이 실행하는 모의 시험임을 결과에 구분합니다.
